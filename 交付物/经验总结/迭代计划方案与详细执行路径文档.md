## 一、迭代策略回顾

### 1.1 总体策略
AI Factory Creator 采用**分期迭代交付**策略：
1. **先跑通核心闭环**：3 个月内交付模型管理 → 布局编辑 → 数据绑定的完整链路。
2. **再根据反馈优化**：标品初版发布后，根据实际项目试用反馈做针对性 Bug 修复和部署优化。
3. **后续逐步扩展**：P1/P2 高级功能按需排入后续迭代计划。

### 1.2 策略选择理由
- **团队规模小（3 人）**，不适合长期并行开发多个模块，适合聚焦 Sprint 逐个突破。
- **产品处于 0→1 阶段**，核心价值需要尽快验证，不适合瀑布式长周期。
- **技术底座成熟（Omniverse）**，基础 3D 能力无需从零开发，可快节奏交付。

## 二、迭代执行路径

### 2.1 Sprint 0 - 需求与设计（2026.03 ~ 04 初）

**执行路径**：
```
业务调研 → PRD 编写 → 技术预研 → 架构设计 → 需求评审
```

**关键产出**：
- [PRD 主档及 7 个附录](../../prds/)
- [8 份项目背景文档](../../docs/)
- 技术架构与数据模型设计

**执行经验**：
- Omniverse 平台调研应在 PRD 编写前完成，确保需求的技术可行性。
- 数据模型设计（8 个核心对象）的前期投入在后续开发中持续受益，减少了返工。

### 2.2 Sprint 1 - 核心能力开发（2026.04）

**执行路径**：
```
模型库 UI 搭建 → USD 上传/解析 → 项目管理 CRUD
→ 基础编辑工具（选择/移动/旋转/缩放）→ 多视角系统
```

**关键产出**：
- 3D 资产模型库可上传、浏览、查看详情
- 工厂项目可创建、保存、配置基础信息
- 3D 场景中可进行基础的对象选择和变换操作

**执行经验**：
- USD 文件解析是最先突破的技术难点——不同来源的 USD 文件结构差异大，需要制定标准化的导入规范。
- 前端（卢棋文）和后端（蒋言明）在模型数据接口设计上做了充分的前期对齐，避免了后期的接口返工。

### 2.3 Sprint 2 - 编辑与绑定（2026.05）

**执行路径**：
```
拖拽式布局编辑 → 撤销/重做栈 → 数据绑定框架
→ 字段映射配置 → 绑定校验引擎 → 用户管理/系统配置
```

**关键产出**：
- 完整的拖拽式布局编辑交互
- 数据绑定配置与校验能力（B7 子模块）
- 系统管理基础功能（用户管理、参数配置）

**执行经验**：
- 数据绑定是整个产品最复杂的功能点，设计期间反复迭代了绑定类型矩阵和节点聚合状态机制。
- 撤销/重做的操作历史栈在 3D 场景下的实现比预期复杂（需要处理 USD 层的原子操作）。

### 2.4 Sprint 3 - 初版打磨（2026.06）

**执行路径**：
```
全链路联调 → UI 细节打磨 → 异常边界处理
→ 性能测试 → 操作手册编写 → 打包发布
```

**关键产出**：
- V1.0.0 可部署版本包
- 操作手册
- 自动化测试报告

**执行经验**：
- 全链路联调发现了几个 B2→B7 的交互断层（如新建实例后自动触发绑定配置面板），在 Sprint 3 初期集中修复。
- 性能测试结果好于预期（1000 设备场景加载 ~7.2s）——得益于 Omniverse 自身的渲染优化能力。

### 2.5 Sprint 4 - 部署优化与维护（2026.07 ~ 10）

**执行路径**：
```
试用反馈收集 → Bug 优先级排序 → 批量修复
→ 部署环境配置优化 → 性能调优
```

**关键产出**：
- 累计修复 Bug 约 7 个（2 Major + 5 Minor）
- 部署环境配置文档完善
- 性能调优（大场景加载速度提升 ~15%）

**执行经验**：
- 维护投入（10 人天）远低于预期——说明初版质量控制和测试覆盖比较到位。
- 部署环境配置是用户上手的第一道门槛，后续迭代应优先完善一键部署/自动配置能力。

## 三、迭代节奏总结

| Sprint | 周期 | 时长 | 功能点数 | 效率（功能点/周） | 质量（遗留 Bug） |
|--------|------|:---:|:---:|:---:|:---:|
| Sprint 0 | 03~04 初 | 4 周 | — | — | — |
| Sprint 1 | 04 | 4 周 | 16 | 4.0 | 3 Minor |
| Sprint 2 | 05 | 4 周 | 22 | 5.5 | 2 Major + 2 Minor |
| Sprint 3 | 06 | 4 周 | 联调+打磨 | — | 全部修复 |
| Sprint 4 | 07~10 | 零星 | 维护 | — | 0 |

**结论**：
- Sprint 2 效率最高（5.5 功能点/周），原因是数据绑定框架复用了 Sprint 1 的数据模型基础。
- 3 人小团队在 3 个月内交付 22 个 P0 功能点，节奏紧凑但可维持。

## 四、后续迭代建议

1. **P1 功能分批交付**：37 个 P1 功能点建议分 2 个 Sprint（各 6 周），优先交付"用户高频使用"的高级编辑和模板库。
2. **自动化测试引入**：当前全手工测试，后续功能点增加后测试成本将线性增长，建议在 V1.1 引入 UI 自动化测试。
3. **用户反馈闭环**：建立"试用 → 反馈 → Bug 跟踪 → 修复 → 验证"的标准化流程。
4. **文档同步机制**：PRD 与代码一致性需要持续维护，建议在 CI 中增加 PRD 引用检查。
