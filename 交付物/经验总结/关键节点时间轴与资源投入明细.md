## 四、资源投入分析

### 4.1 关键发现
1. **前/后端投入均衡**：卢棋文（3.5 人月）≈ 蒋言明（3.5 人月），前后端不存在瓶颈不对等现象。
2. **产品全程参与**：原野在 Sprint 周期的每个阶段都保持了 0.5 人月的投入，确保了需求持续澄清和验收质量。
3. **维护投入极低**：侯一鸣 0.5 人月（10 人天）说明初版代码质量和测试覆盖到位，未产生大量技术债务。
4. **无并行 Sprint**：由于团队规模仅 3 人，所有 Sprint 串行执行，这也是工时计算的基础前提。

### 4.2 效率指标

| 指标 | 数值 | 计算方式 |
|------|------|----------|
| 初版总人月 | 9.5 | Sprint 0~3 合计 |
| 初版交付功能点 | 22（P0） | 全部完成 |
| 人均月交付功能点 | 2.3 | 22 / 9.5 |
| 单功能点人月 | 0.43 | 9.5 / 22 |
| Bug 率（初版发布时） | 7 个（无严重） | 22 功能点对应 |

### 4.3 经验结论
- **3 人团队 3 个月交付 22 个 P0 功能点，效率合理**。
- **前/后端 1:1 配比**在 3D 工具类产品中是合适的（3D 交互开发需要等量的前端投入）。
- **产品持续投入 0.5 人月/Sprint**是保证需求不偏差的最小投入底线。
